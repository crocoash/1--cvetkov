# Штрихкоды в макетах теряются при заливке файлов конфигурации

Инструкция для Claude Code, работающего со второй базой 1С (доставка правок = выгрузка/загрузка
конфигурации в файлы). Разобрано и проверено на базе `work` (УТП для Украины 1.2, платформа
8.3.25.1374) 30.07.2026. Здесь только подтверждённые факты — не переизобретай диагностику заново.

## Симптом

После каждой загрузки конфигурации из файлов в базе пропадает штрихкод в печатных формах:
в макете на его месте пустая рамка (в Конфигураторе — рисунок с типом «Объект» без содержимого).
Пользователь может описывать это как «затирает фото/картинку на макете».

Сопутствующие проявления:
- в коде падает `ОбластьПодвал.Рисунки.D1.Объект.ТипКода = ...` — «Значение не является значением
  объектного типа» либо рисунок не находится по имени;
- сообщение «Компонента 1С:Печать штрихкодов не установлена на данном компьютере!» — это **другая**
  проблема, см. раздел «Ложные следы».

## Причина

Штрихкод в таких конфигурациях — не картинка, а **ActiveX-объект внутри макета**
(в `Template.xml` это `<drawing><drawingType>Object</drawingType>` с блобом
`<object xsi:type="xs:base64Binary">`). Выгрузка конфигурации в файлы такие рисунки калечит
двумя способами:

1. **не пишет блоб `<object>`** — рисунок остаётся, объекта нет;
2. **не пишет `namedItem`** — рисунок теряет имя, а код обращается к рисункам по имени.

Обратная загрузка такого файла сносит объект и в базе. Потерю пункта 2 легко не заметить: блоб
на месте, проверка «объект есть» проходит, а печать всё равно ломается.

Картинки (`drawingType=Picture`, внутри PNG/JPEG) выгружаются корректно и **не теряются никогда** —
если пользователь говорит, что «пропало фото», почти наверняка речь про ActiveX-рамку.

## Порядок работы (главное)

```
1. Выгрузили конфигурацию в файлы
2. powershell -File _tools\fix-barcodes.ps1 -Применить
3. powershell -File _tools\check-barcodes.ps1
4. Заливать в базу ТОЛЬКО если check написал «Все внедрённые объекты на месте»
5. F7 в Конфигураторе (обновить конфигурацию базы данных)
```

Если шаги 2–3 пропустить и залить файлы как есть — штрихкоды снесёт снова. Никакого «само
восстановится» не бывает: в первой базе имя рисунка `D1` не выгружалось **ни в одном** из 14
коммитов истории, то есть печать ломалась после каждой заливки с самого начала.

## Настройка под конкретную конфигурацию

Скрипты в `_tools` переносимы, но **таблицу имён надо задать под свою конфигурацию**.
В `fix-barcodes.ps1` есть хеш-таблица `$ИменаОбъектов`: `путь макета в выгрузке` → `имя рисунка`.

Как её заполнить:

1. Найти макеты с ActiveX:
   ```
   grep -rl "drawingType>Object<" --include="*.xml" .
   ```
2. Найти, под какими именами код обращается к этим рисункам:
   ```
   grep -rn "Рисунки\.[A-Za-zА-Яа-я0-9_]*\.Объект" --include="*.bsl" .
   ```
   Обычные формы лежат в `Form.bin` — grep их не берёт, читать так (текст внутри в UTF-8):
   ```powershell
   $t=[Text.Encoding]::UTF8.GetString([IO.File]::ReadAllBytes('...\Ext\Form.bin'))
   ($t -split "`r?`n") | Where-Object { $_ -match 'Рисунки\.' -and $_.TrimStart() -notmatch '^//' }
   ```
3. Сопоставить макет и имя: найти в коде `ПолучитьМакет("...")` / `ПолучитьОбщийМакет("...")`
   и посмотреть, какие `Рисунки.<Имя>.Объект` используются ниже в том же блоке.
4. Прописать пары в `$ИменаОбъектов` и прогнать `fix-barcodes.ps1` без `-Применить`
   (предпросмотр), затем с `-Применить`.

## Два класса компоненты — важно

| ProgID | CLSID | состояние |
|---|---|---|
| `V8.Barcod.2` | `{44F02ECC-3C4A-4473-AD07-B0DB9048AD9F}` | **рабочий**, платформа рисует |
| `V8.Barcod.1` | `{5C4EB2BC-9BA3-4C78-8799-8322EB1B0BEA}` | объект создаётся, но платформой **не рисуется** |

Оба класса живут в одной и той же `1CBarCod.dll`. Если в макете объект старого класса — штрихкод
не появится, сколько ни чини блоб. Лечится подстановкой эталона:
`fix-barcodes.ps1 -Применить -ЗаменитьСтарыйКласс`.

Эталон лежит в `_tools\barcode-object.xml` (рабочий `V8.Barcod.2`, взят из макета
`Простир_Процентовка` первой базы). Он несёт свои настройки шрифта и размеров, поэтому после
подстановки в чужой макет **обязательно проверить печать глазами** — штрихкод может вылезти не того
размера. Свой эталон делается копированием блока `<object ...>...</object>` из целого макета в файл.

CLSID внутри блоба лежит со смещения 19 (16 байт GUID) — так его читают оба скрипта.

## Ложные следы (проверено, не тратить время)

- **«Компонента не установлена на данном компьютере»** — это про создание COM-объекта в коде
  (`Новый COMОбъект("V8.Barcod.1")`), а не про макет. Компонента `1CBarCod.dll` **32-битная**,
  её CLSID зарегистрирован только в 32-битной ветке реестра (`WOW6432Node`). Из 64-битного клиента
  1С она недоступна принципиально — `REGDB_E_CLASSNOTREG`, и никакой регистрацией это не лечится.
  Клиент для таких баз запускать только x86 (`C:\Program Files (x86)\1cv8\...\bin\1cv8.exe`,
  либо зафиксировать «Разрядность клиента приложения = x86» в списке баз).
- Проверка регистрации одной командой (должно быть OK в 32 битах, FAIL в 64):
  ```powershell
  & C:\Windows\SysWOW64\WindowsPowerShell\v1.0\powershell.exe -NoProfile -Command `
    'try { $x = New-Object -ComObject V8.Barcod.1; "OK" } catch { "FAIL: " + $_.Exception.Message }'
  ```
- **ProgID-ключи реестра общие** для 32- и 64-битного представлений (редиректится только `CLSID`).
  Отсутствие `HKLM:\SOFTWARE\Classes\WOW6432Node\V8.Barcod.1` при `Test-Path` из 64-битного
  процесса — норма, а не поломка. Не «чинить» это дописыванием ключей.
- **Заменить ActiveX на программно сгенерированную картинку нельзя.** У компоненты нет метода
  отдачи изображения: только свойства (`ТипКода`, `Сообщение`, `ТекстКода`, `ОтображатьТекст`,
  `УголПоворота`, цвета) и `УстановитьШрифт`/`УстановитьЦвет*`. Она умеет рисовать себя лишь как
  OLE-объект. Уйти от проблемы можно только сменой технологии: Native-компонента генерации
  штрихкодов (БСП/ИТС) или штрихкодовый TTF-шрифт — это отдельная большая задача.
- Права на файл dll, ACL, Defender/ASR, AppLocker к этому не имеют отношения — проверено.

## Грабли инструментов (Windows PowerShell 5.1)

- `.ps1` с кириллицей **обязан быть UTF-8 с BOM**, иначе PS 5.1 читает его как ANSI и падает на
  разборе строк. Починка:
  ```powershell
  $t=[IO.File]::ReadAllText($p,[Text.Encoding]::UTF8)
  [IO.File]::WriteAllText($p,$t,(New-Object Text.UTF8Encoding $true))
  ```
- Кириллицу в аргументах не передавать через `powershell -Command "..."` — двойные кавычки съедают
  `$_` и ломают вложенный код. Запускать через `-File` со скриптом.
- `Template.xml` писать только UTF-8 **с BOM** (`New-Object Text.UTF8Encoding $true`).
- Строки продолжения base64 в `Template.xml` обязаны начинаться с нулевой позиции строки. Любой
  добавленный отступ внутри блока даёт при загрузке «Ошибка формата потока».
- После правки `Template.xml` всегда проверять, что XML остался валидным (`XmlDocument.Load`) —
  в `fix-barcodes.ps1` это уже встроено.

## Быстрый старт во второй базе

```
1. Скопировать _tools\{check-barcodes.ps1,fix-barcodes.ps1,barcode-object.xml} в _tools репозитория
2. powershell -File _tools\check-barcodes.ps1        # что вообще есть и что сломано
3. Заполнить $ИменаОбъектов в fix-barcodes.ps1 (см. «Настройка под конкретную конфигурацию»)
4. powershell -File _tools\fix-barcodes.ps1          # предпросмотр
5. powershell -File _tools\fix-barcodes.ps1 -Применить
6. powershell -File _tools\check-barcodes.ps1        # должно быть «Все внедрённые объекты на месте»
7. Заливка в базу + F7 + проверить печать глазами
```
