# Перенос канала «Claude видит данные 1С» в другой проект

Комплект для переноса. Здесь описано, из чего канал состоит, что копировать файлами, что дописать
руками и что сделать на машине с 1С. Рабочий экземпляр — в этом репозитории, его разбор для
пользователя канала лежит в [ЗапросыКБазе.md](ЗапросыКБазе.md); тот документ отвечает на вопрос
«как спрашивать», этот — «как поставить».

## Что канал делает

| | |
|---|---|
| `query` | произвольный запрос на языке запросов 1С, ответ таблицей/JSON |
| `meta` | поля, табличные части, движения по регистрам, значения перечислений |
| `edit` | правка справочников, по умолчанию в режиме проверки «было → станет» |
| `ping` | связь |

Смысл в том, что **вопрос про данные становится запросом, а не вопросом пользователю**. Без канала
любое «а сколько у нас заказов без оплаты» упирается в человека у Конфигуратора, и разбор идёт
по догадкам из XML выгрузки.

## Из чего он состоит

```
Claude  --HTTPS-->  [ прокси на сайте ]  --HTTPS-->  HTTPСервис в 1С
                       необязательно                    |  action = query | meta | edit
                                                        v
                                          ОбщийМодуль.ЧтениеДанныхБазы
                                          ОбщийМодуль.ИзменениеСправочников
```

Три слоя, из них обязательны два. **Прокси на сайте нужен только тогда, когда базу нельзя
показать моей машине напрямую.** В cvetkov так и вышло: firewall на 8443 пускает лишь подсети
Telegram и исходящий адрес хостинга, поэтому спрашивает сайт, а я читаю его пересказ. Если в целевом
проекте база доступна с моего адреса (или её можно туда пустить одним правилом firewall), прокси
не нужен вовсе — сервис ниже умеет отвечать и на GET, то есть его хватает `WebFetch`.

## Что должно быть в целевой базе

| | проверка |
|---|---|
| публикация базы на веб-сервере | есть ли `default.vrd`, отвечает ли что-нибудь по `/hs/` |
| HTTP-сервисы в публикации | элемент `<httpServices>` в `default.vrd` |
| режим совместимости | HTTP-сервисы работают и в режиме 8.2: в `1-_garazh` (УТ 2.3.17, `CompatibilityMode = Version8_2_13`) уже опубликован `HTTPОбменССайтомAPI` для Magento |

**Если публикация уже есть — переносится за один заход:** два общих модуля, один HTTP-сервис,
одна роль. Если публикации нет, основная работа — она, а не код; порядок разобран
в [ЗаданиеПубликацияВебхука.md](ЗаданиеПубликацияВебхука.md) (IIS, `Web-CGI`, `wsisapi.dll`,
`Usr`/`Pwd` в `default.vrd`, отдельный сайт и порт).

Когда в базе **уже есть** опубликованный HTTP-сервис (случай garazh), дешевле не заводить новый,
а дописать в его модуль разбор `action` из блока ниже и добавить шаблон URL. Публикацию тогда
трогать не нужно совсем.

## Шаг 1. Два общих модуля — копируются файлами как есть

```
CommonModules/ЧтениеДанныхБазы/Ext/Module.bsl        686 строк
CommonModules/ЧтениеДанныхБазы.xml
CommonModules/ИзменениеСправочников/Ext/Module.bsl   535 строк
CommonModules/ИзменениеСправочников.xml
```

Оба **не зависят ни от чего в этой конфигурации**: ни от Телеграма, ни от типовых общих модулей.
Внутри только платформенные объекты (`Запрос`, `Метаданные`, `Справочники[…]`), поэтому в любую
другую конфигурацию они кладутся без правок.

Что поправить в `.xml`: новый `uuid` (`[guid]::NewGuid()`), остальные свойства оставить —
`Server = true`, `ServerCall = false`, `Privileged = false`. Привилегированный режим включается
внутри кода первой строкой, а не свойством модуля: так видно, где именно он нужен.

Дальше — **регистрация в `Configuration.xml`**, в `ChildObjects`, среди остальных `CommonModule`:

```xml
<CommonModule>ЧтениеДанныхБазы</CommonModule>
<CommonModule>ИзменениеСправочников</CommonModule>
```

Без этой строки объект в конфигурацию не попадёт, и загрузка из файлов пройдёт молча — файл есть,
объекта нет.

`ИзменениеСправочников` зовёт `ЧтениеДанныхБазы.ЗначениеИзJSON()` — разбор `{"type":"ссылка",…}`
общий у обоих, поэтому переносить их надо парой. Нужно только чтение — второй модуль можно
не брать, но тогда убрать и ветку `edit` из сервиса.

## Шаг 2. HTTP-сервис

В cvetkov отдельного сервиса нет: команды сайта заходят в `HTTPСервис.ТелеграмВебхук` вместе
с вебхуком Telegram и разводятся по секрету (у Telegram свой заголовок, у сайта — `X-Site-Token`).
Так вышло исторически — **платформа не вызывала обработчик второго шаблона `/cmd`**, хотя знала
о нём (на несуществующий путь отвечала 404, а на `/cmd` — 403, при этом в журнале не появлялось
ни одной записи). Разбираться дальше было дороже, чем не заводить второй адрес.

Для переноса это не нужно: ниже — самостоятельный сервис, без телеграмной обвязки.

### `HTTPServices/ЗапросКБазе.xml`

```xml

	<HTTPService uuid="1791519e-9739-490c-be9f-db2b151ec80b">
		<Properties>
			<Name>ЗапросКБазе</Name>
			<Synonym>
				<v8:item>
					<v8:lang>ru</v8:lang>
					<v8:content>Запрос к базе</v8:content>
				</v8:item>
			</Synonym>
			<Comment>Служебное чтение данных базы снаружи. Адрес: https://&lt;хост&gt;/&lt;база&gt;/hs/db/cmd</Comment>
			<RootURL>db</RootURL>
			<ReuseSessions>DontUse</ReuseSessions>
			<SessionMaxAge>20</SessionMaxAge>
		</Properties>
		<ChildObjects>
			<URLTemplate uuid="47fb5f16-d5b1-4772-8708-462806d4fc0d">
				<Properties>
					<Name>Команда</Name>
					<Synonym/>
					<Comment/>
					<Template>/cmd</Template>
				</Properties>
				<ChildObjects>
					<Method uuid="dabdff7f-654b-4193-be94-aa3f5972e767">
						<Properties>
							<Name>Принять</Name>
							<Synonym/>
							<Comment/>
							<HTTPMethod>POST</HTTPMethod>
							<Handler>Принять</Handler>
						</Properties>
					</Method>
					<Method uuid="9700f52f-d3c6-4432-a62f-b1cf164afc4d">
						<Properties>
							<Name>Прочитать</Name>
							<Synonym/>
							<Comment/>
							<HTTPMethod>GET</HTTPMethod>
							<Handler>Принять</Handler>

```

Два метода на один обработчик: POST — для длинных запросов и прокси, GET — чтобы канал был
доступен из `WebFetch` без всякого прокси. uuid здесь свежие, но при переносе в третий проект
их всё равно перегенерировать.

Плюс строка в `Configuration.xml`: `<HTTPService>ЗапросКБазе</HTTPService>`.

### `HTTPServices/ЗапросКБазе/Ext/Module.bsl`

		КонецЕсли;

		// тому, кто запрос писал. Канал служебный, покупатель этого не видит.
		ЗаписьЖурналаРегистрации("База.Запрос",
			УровеньЖурналаРегистрации.Ошибка, , ,

			+ ПодробноеПредставлениеОшибки(ИнформацияОбОшибке()));

// сами: модулям ниже нужны Булево и Структура, а "ids=1" - это строка "1".

Модуль писался здесь и **на базе не проверялся** — на этой машине ни Конфигуратора, ни платформы
нет. Разбор GET-параметров через `Запрос.ПараметрыЗапроса` взят из синтакс-помощника, а не из
наблюдения; в рабочем экземпляре cvetkov используется только POST. Первым делом после загрузки —
`?action=ping`, вторым — `?action=meta&object=*&like=склад`.

## Шаг 3. Роль и пользователь публикации

Пользователь публикации служебный, «Полных прав» у него быть не должно — публикация смотрит
в интернет. Ему нужна одна роль с единственным правом: вызвать этот сервис.

`Roles/ДоступКЗапросам/Ext/Rights.xml`:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<Rights xmlns="http://v8.1c.ru/8.2/roles" xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance" xsi:type="Rights" version="2.18">
	<setForNewObjects>false</setForNewObjects>
	<setForAttributesByDefault>false</setForAttributesByDefault>
	<independentRightsOfChildObjects>false</independentRightsOfChildObjects>
	<object>
		<name>HTTPService.ЗапросКБазе.URLTemplate.Команда.Method.Принять</name>
		<right>
			<name>Use</name>
			<value>true</value>
		</right>
	</object>
	<object>
		<name>HTTPService.ЗапросКБазе.URLTemplate.Команда.Method.Прочитать</name>
		<right>
			<name>Use</name>
			<value>true</value>
		</right>
	</object>
</Rights>
```

Прав на справочники и документы роли **не нужно**: код внутри первой строкой включает
привилегированный режим. Проверка «свой — чужой» здесь одна, токен, и дублировать её ролями
значило бы держать два списка вместо одного.

Роль тоже регистрируется в `Configuration.xml` (`<Role>ДоступКЗапросам</Role>`), а пользователь
с ней заводится **в базе**, в Конфигураторе: аутентификация 1С:Предприятия, длинный пароль,
«показывать в списке выбора» снять. Пароль идёт в `Usr`/`Pwd` строки соединения в `default.vrd`.

## Шаг 4. Как звать

Прямо, если база видна с моей машины (GET, поэтому годится `WebFetch`):

```
https://<хост>:8443/<база>/hs/db/cmd?token=…&action=meta&object=*&like=заказ
https://<хост>:8443/<база>/hs/db/cmd?token=…&action=query&q=ВЫБРАТЬ ПЕРВЫЕ 20 Код, Наименование ИЗ Справочник.Склады
```

POST-ом — когда запрос длинный:

```
curl -sk -X POST https://<хост>:8443/<база>/hs/db/cmd \
     -H 'X-Site-Token: …' -H 'Content-Type: application/json; charset=utf-8' \
     -d '{"action":"query","q":"ВЫБРАТЬ ПЕРВЫЕ 20 Код, Наименование ИЗ Справочник.Склады"}'
```

Кириллицу в GET кодировать `urllib.parse.quote`. `WebFetch` кеширует ответ на 15 минут — менять
`&u=N` на каждый вызов, иначе видно старый. `curl` с токеном прямо в URL отбивает
permission-классификатор Claude Code — для GET идти через `WebFetch`, для POST токен слать
заголовком, как выше.

## Шаг 5. Прокси на сайте — если напрямую нельзя

Нужен ровно тогда, когда базу не пустить к моему адресу: динамический IP, чужой firewall,
политика «наружу торчит только сайт». Тогда единственный адрес, которому база доверяет, —
исходящий адрес хостинга, и сайт становится проводником.

Файлы в `../modx/shop/` (это рабочие, из cvetkov):

| | |
|---|---|
| `inc_1c_cmd.php` | `cmd1c($payload, $timeout)` — POST JSON в 1С, разбор ответа, чтение чужих ошибок |
| `debug_1c_query.php` | `query` и `meta`: таблица/csv/json, ширина колонок по `mb_strlen` |
| `edit_1c_catalog.php` | `edit`: разбор `items`, показ «было → станет» |
| `debug_1c_log.php` | журнал регистрации 1С и `&ping1c=1` — проверка связи |

Что править при переносе: `CMD_1C_URL`, `CMD_1C_TOKEN` в `inc_1c_cmd.php` и `Q1C_TOKEN`
в каждом из скриптов. Дальше — разобранное в них же:

* **токен уходит и заголовком, и в теле.** Заголовок — основной путь, тело — запасной: 09.08.2026
  1С отвечала 403 на запрос с верным заголовком, то есть до сервиса он не доходил;
* **проверка сертификата выключена осознанно** (`CURLOPT_SSL_VERIFYPEER = false`): у базы
  самоподписанный сертификат, канал защищён токеном, а не именем в сертификате;
* **`no-store` в заголовках ответа.** Перед сайтом кеширующий nginx с `max-age=604800`: без этого
  один и тот же GET неделю отдаёт первый ответ, и запрос «не выполняется»;
* **страница ошибки IIS приходит в cp1251** и молча съедается `htmlspecialchars()` — получается
  пустая красная плашка вместо текста. Чистится у источника, `cmd1cReadable()`.

## Что канал может и чего не может

**Читать — произвольным текстом запроса, и это осознанно.** В языке запросов 1С нет ни `INSERT`,
ни `UPDATE`, ни `DELETE`, а `Запрос.Текст` никакого кода не выполняет — он разбирается построителем.
Изменить данные этим путём нельзя в принципе, худшее от кривого запроса — нагрузка на сервер
и мусор в ответе. Белый список готовых запросов стоил бы круга «правка → push → pull → загрузка
конфигурации» на КАЖДЫЙ новый вопрос, а вопросы возникают по ходу разбора, а не заранее.

**Писать — только справочники, только с `apply`.** Документы, регистры и константы недоступны
намеренно: документ — это движения, проведение и последствия в отчётности, снаружи ему не место.
Физического удаления нет, только пометка; удаляет пользователь обработкой, которая проверит ссылки.

Ограничители, которые надо перенести вместе с кодом, а не «упростить»:

* строк в ответе — `limit`, по умолчанию 500, максимум 5000;
* каждый вызов пишется в журнал регистрации: `База.Запрос` (текст, число строк, время)
  и `База.Запись` (состав изменений). Это единственный способ увидеть, кто и что спрашивал;
* пачка правки — не больше 200 элементов;
* строка длиннее реквизита **не пишется, а отклоняется**: платформа усекает такое молча,
  и по усечённому ключу потом ломается поиск.

Чего в канале нет намеренно: **ограничения по времени выполнения**. Оборвать уже запущенный запрос
платформа не даёт, поэтому тяжёлый запрос честно займёт рабочий процесс до конца. Размен
осознанный — канал служебный, вызывающих двое. Практический вывод: соединения по большим
регистрам сразу ограничивать периодом.

## Ловушки

| | |
|---|---|
| **403 с пустым телом подменяет IIS** своей страницей. Отличить своё 403 от чужого — по полям: `Модуль IsapiModule`, `Обработчик 1C Web-service Extension` значит, что запрос прошёл через 1С |
| **404 после загрузки конфигурации** — не регресс публикации, а отставание базы: шаблон URL есть в файлах, но в базу не загружен. Новый шаблон это изменение метаданных, одного F7 без принятия структурных изменений мало |
| **401** — не прописаны `Usr`/`Pwd` в `default.vrd` |
| **`webinst` не публикует HTTP-сервисы**: `<httpServices>` в сгенерированном `default.vrd` нет вообще. Дописывать руками, атрибут `pointEnableCommon` у него **не принимается** (у `<ws>` валиден) — 1С отвечает 500 «Ошибка при разборе дескриптора виртуальных ресурсов» |
| **таймаут при исправной публикации** — firewall по адресу источника. Проверять не с рабочей машины, а с того адреса, которому положено ходить |
| **ссылки отдаются представлением** — обращение к объекту на каждое значение, N+1. На пятистах строках заметно: брать `Ссылка.Код` или `ids=1` |
| **значений перечислений в базе нет вовсе** — только `meta`, запросом их не увидеть |

## Что дописать в CLAUDE.md целевого проекта

Без этого абзаца канал существует, но не используется: следующая сессия по привычке спросит
пользователя или полезет угадывать имена таблиц по XML.

```markdown
## Данные базы видны — спрашивать запросом, а не пользователя

Конфигурация лежит файлами, а данные рабочей базы читаются вживую:

    https://<хост>/<база>/hs/db/cmd?token=<токен>
       &action=query&q=ВЫБРАТЬ ПЕРВЫЕ 20 Код, Наименование ИЗ Справочник.Склады
       &action=meta&object=Документ.ЗаказПокупателя   поля, табличные части, движения
       &action=meta&object=*&like=заказ               список объектов метаданных

Правило: любой вопрос про данные сначала задавать базе. «Сколько заказов без оплаты», «какие
бывают статусы», «что лежит в этом регистре» — это запрос, а не вопрос пользователю и не догадка
по XML. Имена таблиц и полей брать из meta: угадывать их по выгрузке дороже и ошибочнее.

Кириллицу кодировать urllib.parse.quote; &u=N менять на каждый вызов, иначе WebFetch отдаст свой
кеш. Справочники правятся через action=edit, и **по умолчанию не пишется ничего**: сначала без
apply, показать пользователю «было → станет», и только потом писать.
```

## Порядок переноса одним списком

1. скопировать два общих модуля с новыми uuid, зарегистрировать в `Configuration.xml`;
2. создать `HTTPServices/ЗапросКБазе` по образцу выше, вписать свой токен, зарегистрировать;
3. создать роль, зарегистрировать;
4. снимок и push;
5. на машине с 1С: `git pull`, загрузка конфигурации из файлов, **принять структурные изменения**
   (новые объекты метаданных, F7 недостаточно);
6. в базе: пользователь публикации с одной ролью, `Usr`/`Pwd` в `default.vrd`;
7. если публикации не было — отдельно IIS + `wsisapi.dll` + `<httpServices>`
   (см. [ЗаданиеПубликацияВебхука.md](ЗаданиеПубликацияВебхука.md));
8. проверка: `?action=ping` → `?action=meta&object=*` → реальный запрос;
9. дописать абзац в `CLAUDE.md` целевого проекта.
