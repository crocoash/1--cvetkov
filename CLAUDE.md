## База и Конфигуратор — на другой машине

**Здесь только файлы выгрузки. Ни базы, ни Конфигуратора на этом компьютере нет.**

Перенос идёт **через GitHub**: `git@github.com:crocoash/1--cvetkov.git`, ветка `main`. Здесь коммит
и push, на машине с 1С — `git pull` и загрузка конфигурации из файлов. Обратная выгрузка из
Конфигуратора едет тем же путём в обратную сторону.

Что из этого следует:

* Между «я правлю файл» и «правка в базе» есть **два лишних шага — push отсюда и pull там**.
  Push делает `snapshot.ps1`; правка существует только на этом диске, пока не отправлена.
* Проверить результат в базе я не могу в принципе: ни запустить Конфигуратор, ни синтаксически
  проверить модуль, ни посмотреть, что реально загрузилось. Всё, что я говорю о **поведении** базы, —
  вывод из кода, а не наблюдение. Проговаривать это, а не выдавать за факт.
  Это про код; **данные** базы с 16.08.2026 читаются напрямую — см. «Данные базы видны» ниже.
* Эта папка **всегда может отставать от базы**: пользователь мог доработать в Конфигураторе на своей
  машине и ещё не перенести выгрузку сюда. Отсюда правило «перед правкой любого файла — прочитать
  его текущее содержимое» становится жёстче: в начале работы делать `git fetch` и смотреть, не
  появилось ли на `origin/main` новой выгрузки.
* **Штрихкоды чинить обязательно здесь, до переноса** (fix→check). На той машине скриптов нет,
  а заливка в базу калечит объекты в макетах уже необратимо.
* Снимок в git — единственная страховка. Перезапись папки новой выгрузкой с той машины откатывает
  всё непринятое молча.

## Данные базы видны — спрашивать запросом, а не пользователя

Конфигурация здесь лежит файлами, а **данные** рабочей базы читаются вживую, с этой машины,
через сайт. Выгружать базу для этого не нужно и не надо: `.dt` — закрытый бинарник, платформы
на маке нет, а GitHub файл больше 100 МБ не примет (разбор — в ответе от 16.08.2026).

```
https://cvetkovtm.com/assets/shop/debug_1c_query.php?token=e4cfdff6ad370ca2f0e26d8eb82bcda9
   &q=ВЫБРАТЬ ПЕРВЫЕ 20 Код, Наименование ИЗ Справочник.Склады
   &meta=Документ.ЗаказПокупателя     поля, табличные части, движения по регистрам
   &meta=*&like=заказ                 список объектов метаданных
```

Цепочка: я → сайт → `inc_1c_cmd.php` → `tg.cvetkovtm.com:8443` → `HTTPСервис.ТелеграмВебхук`
(действия `query`, `meta`) → `ОбщийМодуль.ЧтениеДанныхБазы`. Напрямую с мака в базу не
постучаться: firewall на 8443 пускает только подсети Telegram и исходящий IP хостинга.
Проверено 16.08.2026: запрос по справочнику — 2 мс в 1С, 92 мс полный круг.

**Правило: любой вопрос про данные сначала задавать базе.** «Сколько заказов без оплаты»,
«какие бывают статусы», «что лежит в этом регистре», «сколько строк в справочнике» — это запрос,
а не вопрос пользователю и не догадка по XML. Имена таблиц и полей брать из `meta`: угадывать
их по выгрузке дороже и ошибочнее.

Как звать из CLI: `curl` с токеном в URL отбивает permission-классификатор — идти через
`WebFetch`; кириллицу в `q`/`meta` кодировать `urllib.parse.quote`; `&u=N` менять на каждый
вызов, иначе `WebFetch` отдаст свой кеш (15 минут). Таблицу результата он показывает дословно,
длинный вывод `meta` пересказывает своими словами — тогда переспросить с `format=json`.

Ограничения канала: не больше 5000 строк в ответе; общего числа строк ответ не даёт
(спрашивать `КОЛИЧЕСТВО(*)`); оборвать запущенный тяжёлый запрос нечем, поэтому соединения
по большим регистрам сразу ограничивать периодом. Каждый запрос пишется в журнал регистрации,
событие **«База.Запрос»**. Подробности и разбор отказов — [_tools/ЗапросыКБазе.md](_tools/ЗапросыКБазе.md).

Ошибки самой базы читаются рядом, тем же приёмом: `shop/debug_1c_log.php?token=…`,
проверка связи — `&ping1c=1`.

### Справочники можно менять — но по умолчанию не пишется ничего

```
https://cvetkovtm.com/assets/shop/edit_1c_catalog.php?token=<тот же>
   &catalog=Справочник.Склады
   &items=[{"code":"000000055","set":{"Наименование":"Склад Барабошово"}}]
   &apply=1     — записать; без него только «было -> станет»
```

Действие `edit`, модуль `ОбщийМодуль.ИзменениеСправочников`. Адресация элемента — `id`,
`code`, `name` или `new`; действия — `set` (реквизиты) и `mark` (пометка удаления).
Тёзки по `name` отклоняются, а не угадываются. Строку длиннее реквизита канал **не пишет**,
а отказывается: платформа усекает такое молча, и это отдельная ловушка ниже.

**Границы намеренные:** только справочники. Документы, регистры и константы недоступны —
документ это движения, проведение и последствия в отчётности, снаружи ему не место
(исключение одно и старое: номер ТТН в заказе). Физического удаления нет, только пометка;
удаляет пользователь обработкой «Удаление помеченных объектов», которая проверит ссылки.

**Порядок работы: сначала без `apply`, показать пользователю «было → станет», и только потом
писать.** Каждый вызов, включая проверку, идёт в журнал регистрации, событие **«База.Запись»**,
с составом изменений. Пачка — не больше 200 элементов за вызов.

## Рабочий цикл и главный риск

Цикл доставки правок **двусторонний** — это главное, что нужно понимать:

1. Claude правит файлы выгрузки, прогоняет fix→check штрихкодов, делает снимок и **push**.
2. На машине с 1С — `git pull`.
3. Пользователь: Конфигуратор → «Загрузить конфигурацию из файлов» → F7 (обновление конфигурации БД).
4. Иногда пользователь сам дорабатывает в Конфигураторе и выгружает конфигурацию **обратно поверх
   папки**, коммитит и пушит; сюда это приезжает по `git pull`.

Шаги 2–3 автоматизированы: на машине с 1С `_tools\apply-config.ps1` делает `git pull`,
затем пакетным Конфигуратором `/LoadConfigFromFiles` + `/UpdateDBCfg -Dynamic-`. Настройки
подключения — `_tools\1c-local.json` (машинный файл, в git не уезжает; создаётся диалогом
`-Настроить`, который читает список баз из `ibases.v8i`). Обратное направление — тот же скрипт
с `-Выгрузить`: `/DumpConfigToFiles` поверх папки и сразу `snapshot.ps1`. База там серверная,
поэтому `.dt` по умолчанию пропускается (страховка — бэкап SQL); принудительно — `-СРезервной`.
Частая помеха — забытый открытый Конфигуратор на другом компьютере, скрипт останавливается
и показывает, где висит сеанс.

**Шаг 4 — источник тихих потерь.** Любая правка файла, не доехавшая до базы до того, как
пользователь выгрузит поверх папки, исчезает без единой ошибки. На соседней конфигурации ловили дважды:

* структурная (новый реквизит документа) — пропала и из файла, и из БД; вылезло только в рантайме
  «Поле не найдено…»;
* обычная (процедура в общем модуле + регистрация объекта в `Configuration.xml`).

Добавление реквизита файлом само по себе ничего не гарантирует, пока пользователь явно не принял
структурные изменения в базе.

### Протокол

* **Перед правкой любого файла — прочитать его текущее содержимое.** Пользователь мог перезаписать
  своей версией. Не полагаться на то, что помню из прошлой сессии.
* **Перед тем как пользователь идёт в Конфигуратор дорабатывать своё — снимок** (см. «Коммитить всегда»).
* **После его выгрузки** — `git diff --stat` против той точки: сразу видно, что откатилось.
  Восстановление: `git checkout <точка> -- <файлы>`. Плюс руками вернуть регистрацию объекта
  в `Configuration.xml`, если пропала.
* **После добавления реквизита / перечисления / нового объекта** — явно напомнить применить
  изменения в базе (F7 недостаточно, если следующим шагом идёт выгрузка из БД обратно).

## Штрихкоды в макетах — проверять ВСЕГДА перед сдачей работы

Штрихкод в печатных формах — не картинка, а **ActiveX-объект** внутри макета
(`<drawing><drawingType>Object</drawingType>` с блобом `<object xsi:type="xs:base64Binary">`
в `Template.xml`). «Выгрузка конфигурации в файлы» выборочно теряет этот блоб и/или имя рисунка
(`namedItem`), а обратная загрузка сносит объект и в базе. Пользователь видит это как
«пропали картинки/фото в макетах» — на месте штрихкода пустая рамка.
Обычные картинки (`drawingType=Picture`) не страдают.

Затронутые макеты в этой базе (4):

```
CommonTemplates/Этикетка/Ext/Template.xml
CommonTemplates/ЭтикеткаБольшая/Ext/Template.xml
DataProcessors/ПечатьЭтикеток/Templates/Макет/Ext/Template.xml
DataProcessors/ПечатьЭтикеток/Templates/Процентовка/Ext/Template.xml
```

**Мой обязательный порядок (не пользователя — мой):**

```
1. Пользователь выгрузил конфигурацию в файлы / я закончил задачу
2. pwsh -NoProfile -File _tools/fix-barcodes.ps1 -Применить
3. pwsh -NoProfile -File _tools/check-barcodes.ps1
4. Отдавать работу и предлагать перенос на машину с 1С ТОЛЬКО после
   «Все внедрённые объекты на месте»; результат писать в ответе
```

Прогонять **при сдаче любой задачи** и **после каждой перевыгрузки пользователем**, без напоминания.
Само оно не восстанавливается: без шага 2 штрихкоды сносит при каждой заливке.

Подробный разбор (два класса компоненты V8.Barcod.1/.2, ложные следы, грабли PowerShell) —
[_tools/ШтрихкодыВМакетах.md](_tools/ШтрихкодыВМакетах.md), лежит здесь же в репозитории.

## Коммитить всегда

Каждую законченную задачу и каждую новую выгрузку фиксировать снимком, не дожидаясь просьбы:

```
pwsh -NoProfile -File _tools/snapshot.ps1 "что сделано"
```

`snapshot.ps1` сам прогоняет fix→check штрихкодов, потом делает `git add -A` + коммит. То есть
шаги 2–3 выше выполняются им автоматически — отдельно их гонять нужно только вне снимка.
Коммит — это ещё и контрольная точка: если пользователь уйдёт в Конфигуратор и выгрузит поверх
папки, незалитые в базу правки тихо откатятся, и вернуть их можно только `git checkout` от снимка.

Отдельно смотреть на **удалённые** файлы в снимке — это главный признак молча потерянных правок.

**Заливать всегда — это часть задачи, а не отдельная просьба.** `snapshot.ps1` после коммита сам
делает `git push origin <ветка>` и красным ругается, если push не прошёл. Не спрашивать разрешения
на отправку: пока коммит не на `origin`, на машине с 1С правок нет. Если снимок делался в обход
скрипта — пушить руками и проверять, что `git status -sb` больше не показывает `ahead`.

### Переносы строк при круге macOS → GitHub → Windows

`.gitattributes` нормализует EOL, и это проверено безопасным: `.xml`/`.bsl` в репозитории лежат
с LF, а в рабочей копии на обеих машинах получаются **CRLF** — ровно так, как их пишет Конфигуратор;
`.html` справки и `.txt` остаются LF (тоже как пишет 1С); `.bin`, картинки и `.mxl` помечены `binary`
и не трогаются вовсе. Единственное отклонение — 5 модулей, у которых в исходной выгрузке переносы
смешанные (`CommonModules/ПроцедурыОбменаТорговляБухгалтерия`,
`DataProcessors/ПомощникНастройкиОбменаДанными`, `ExchangePlans/ОбменССайтомЗаказами`,
`ОбменССайтомТоварами`, `Полный`): после `pull` они приедут целиком в CRLF. Одиночные LF там
разделяют строки кода, а не сидят внутри строковых литералов, поэтому для платформы это безразлично.
Менять `.gitattributes` не нужно; если однажды понадобится байт-в-байт — помечать конкретные файлы
`-text`, а не переписывать правило целиком.

## Новые формы делать управляемыми — их можно писать текстом

В `Configuration.xml`: `DefaultRunMode = OrdinaryApplication`, но
**`UseManagedFormInOrdinaryApplication = true`** — управляемые формы в этой базе открываются
из обычного приложения (их уже 71). Практический вывод: **новую форму не надо просить нарисовать
в Конфигураторе.** Управляемая форма — это три текстовых файла:

```
<Объект>/Forms/<Имя>.xml                 — дескриптор, FormType = Managed, свой uuid
<Объект>/Forms/<Имя>/Ext/Form.xml        — содержимое: AutoCommandBar, ChildItems, Attributes, Commands
<Объект>/Forms/<Имя>/Ext/Form/Module.bsl — модуль с директивами &НаКлиенте / &НаСервере
```

Плюс в XML объекта: `<Form>Имя</Form>` в конец `ChildObjects` (после `TabularSection`) и
`<DefaultForm>DataProcessor.<Объект>.Form.<Имя></DefaultForm>`.

Порядок элементов внутри `<Form>`: `AutoCommandBar`, `ChildItems`, `Attributes`, `Commands`.
Главный реквизит — `<Attribute name="Объект">` с `<MainAttribute>true</MainAttribute>` и типом
`cfg:DataProcessorObject.<Имя>`; тогда `DataPath` пишется как `Объект.Реквизит` и
`Объект.ТабЧасть.Колонка`. Кнопки — явные `<Button>` с `<CommandName>Form.Command.Имя</CommandName>`
внутри `AutoCommandBar` (см. ловушку про «Все действия»), команды — `<Command name="Имя">`
с `<Action>ПроцедураМодуляФормы</Action>`.

Дешёвая проверка перед загрузкой: сверить, что каждому `<Command>` соответствует кнопка и клиентская
процедура `Процедура Имя(Команда)` в модуле формы, а каждый `DataPath` — реально существующий
реквизит или колонка табличной части в XML объекта.

Реквизиты объектов добавляются правкой `<Тип>/<Имя>.xml`: скопировать блок `<Attribute>`,
новый uuid через `[guid]::NewGuid()`.

## Правка бинарных форм (Form.bin)

Обычных форм здесь 2440. Модуль формы **править по файлам можно** — база принимает (проверено
на соседней конфигурации).

Формат: заголовок файла 16 байт (`ff ff ff 7f` | pageSize=0x200 | ver=2 | 0), далее блоки; заголовок
блока — 31 байт ASCII `\r\n%08x %08x %08x \r\n` (docSize, pageSize, nextPageAddr; `0x7fffffff` =
конца нет). Первый блок по адресу 16 — TOC, по 12 байт на элемент (int32 hdrAddr, dataAddr,
`0x7fffffff`). Элементов два: `form` (описание в скобочном формате) и `module` (чистый текст модуля,
UTF-8 с BOM). Заголовок элемента — 20 байт дат + имя в UTF-16LE.

Важное упрощение: TOC и большие документы (модуль на 100+ КБ) хранятся **одним блоком без чанкинга**.
Поэтому repack не требует разбиения на страницы: дописать новый блок в конец файла
(`docSize = pageSize = длина контента`, `nextPageAddr = 0x7fffffff`) и точечно поправить 4 байта
`dataAddr` нужного элемента TOC (offset = начало данных TOC + индекс×12 + 4), остальной файл
не трогать. Round-trip (repack неизменного модуля → unpack → сравнение) даёт побайтовое совпадение —
этим и проверяется скрипт перед реальной правкой.

`unpack1c` / `repack1c` пишутся в scratchpad и воссоздаются по этому описанию за пару минут —
в репозитории их держать не нужно.

**Границы:** модуль формы — можно; типы колонок таблиц значений и элементы формы (скобочная часть
`form`) руками не менять, это делает пользователь в Конфигураторе. Каждый repack оставляет старый
блок «сиротой» — файл растёт, самоисправляется при следующей настоящей выгрузке.

Формы сторонних подсистем, чей код есть только в скомпилированном `Form.bin`, — не читаются;
поведение приходится выводить из модулей объектов. Это проговаривать, а не выдавать догадку за факт.

## Ловушки платформы — проверять сразу

* **Строковые реквизиты и колонки ТЗ молча усекают значение.** Колонка `Строка(15)` примет длинный
  идентификатор и обрежет его — без ошибки. Если по этому значению потом ищут документ, дедуп
  ломается. Правило: ключ поиска строить из фактически сохранённого значения, а не из исходного.
* **Фоновое задание, запущенное из `ПриЗаписи`, работает в незафиксированной транзакции** — отдельный
  сеанс либо не видит документ вообще, либо читает старое состояние. Лечится очередью: `ПриЗаписи`
  только регистрирует объект в регистре сведений (в той же транзакции), разгребает регламентное
  задание. Плюс: если ключ фонового задания занят, повторный запуск молча отбрасывается.
* **Расписание предопределённых регламентных заданий в метаданных не хранится** — после загрузки
  конфигурации его нужно задать в базе. Иначе очередь копится, и это не даёт никакой ошибки.
* **Монопольному обновлению конфигурации БД мешают свои же фоновые задания** — «подождать, пока
  все выйдут» не работает, очередное задание стартует по расписанию прямо во время ожидания.
  Лечится запретом регламентных заданий на уровне ИБ (`apply-config.ps1` делает это сам) и
  завершением их сеансов; загрузке из файлов и `-Динамически` они не мешают.
* **`Попытка … Исключение Возврат`** в типовом коде глотает реальные баги. Если «функция просто
  ничего не делает» — искать такой блок.
* **У управляемых форм в старых конфигурациях команды могут не попадать в «Все действия»** — кнопки
  размещать явным `CommandBar` в `Form.xml`, иначе форма открывается вообще без кнопок.
* **`ОбменДанными.Загрузка` в проверках часто инертен** — если конфигурация не узел плана обмена,
  флаг никто не выставляет.
* **Внедрённые ActiveX-объекты в макетах калечатся выгрузкой в файлы** — см. раздел про штрихкоды выше.
  Компонента «1С:Печать штрихкодов» 32-битная — из 64-битного клиента недоступна в принципе.
* **В `Template.xml` строки продолжения base64 обязаны начинаться с нулевой позиции** — любой отступ
  внутри блока даёт при загрузке «Ошибка формата потока». Сам файл писать только в UTF-8 с BOM.
  После правки макета проверять XML валидатором.

## Типовой профиль оптимизации

Тормоза в формах подбора/списков почти всегда — **N+1 в построчных обработчиках**:
`ПриВыводеСтроки` и `ПриАктивизацииСтроки` дёргают функции с собственными запросами (остатки,
резервы, цвета, характеристики) на каждую строку и на каждую перерисовку, без кэша. Лечение по порядку:

1. кэш в переменных формы на время открытого диалога (обёртки над теми же функциями);
2. один пакетный запрос (`Запрос.ВыполнитьПакет`) на прогрев кэша сразу по всем строкам вместо цикла;
3. тяжёлую разовую работу из `ПриОткрытии` вынести в `ПодключитьОбработчикОжидания(…, 0.1, Истина)` —
   диалог показывается мгновенно (трейд-офф проговорить с пользователем).

## Именование новых объектов

Префикс чужого подрядчика для новых объектов не использовать; существующие объекты с чужими
префиксами не переименовывать — это чужой код с сотнями точек вызова, выгода нулевая, риск реальный.

## Инструменты и среда

* `_tools/snapshot.ps1 ["сообщение"]` — снимок (fix→check штрихкодов + `git add -A` + коммит).
* `_tools/apply-config.ps1` — **только на машине с 1С**: pull + загрузка конфигурации из файлов +
  обновление конфигурации БД. `-Настроить` — выбрать базу, `-Выгрузить` — обратное направление,
  `-БезPull`, `-СРезервной`. Перед монопольным обновлением сам блокирует регламентные задания
  и завершает сеансы фоновых заданий, после — снимает; чужие клиентские сеансы только по
  `-ВыгнатьВсех`, `-НеТрогатьЗадания` отключает. Двойным кликом — `_tools/Обновить базу.cmd`.
  В COM-модели кластера обязанности разделены: **сеансы** (список, завершение) — через агент
  (`ConnectAgent`, порт 1540), **свойства базы** (блокировка заданий, запрет сеансов, код
  разрешения, `UpdateInfoBase`) и `AddAuthentication` — только через соединение с рабочим
  процессом (`ConnectWorkingProcess`, rphost). Агент по базе отдаёт `IInfoBaseShort`, где нет
  ни этих свойств, ни метода; путать эти два объекта — источник ошибок «отсутствует метод
  AddAuthentication» и «не удается найти свойство ScheduledJobsDenied».
* `_tools/fix-barcodes.ps1 -Применить`, `_tools/check-barcodes.ps1` — восстановление и проверка
  ActiveX-объектов в макетах. `_tools/barcode-object.xml` — эталонный блоб.
* Линт: BSL Language Server (jar в git не хранится, ставится по запросу; Java 26 в системе есть).
  Смотреть только Error и только по своим файлам — на типовой конфигурации замечаний десятки тысяч,
  почти всё стилевые hint/info.

**Среда — macOS, PowerShell 7 (`pwsh`, поставлен через `brew install powershell`).**
Скрипты писались под Windows PowerShell 5.1 и работают в обеих средах; `snapshot.ps1` сам определяет
интерпретатор и путь к `git`. Запускать через `pwsh -NoProfile -File`, пути писать через `/`.

Правила по коду скриптов (нужны, чтобы они остались рабочими и на машине с 1С, где PowerShell 5.1):

* `.ps1` с кириллицей сохранять в **UTF-8 с BOM**, иначе парсер 5.1 ломается на первой же
  кириллической строке. Инструмент Write пишет без BOM — дописывать через
  `[System.IO.File]::WriteAllText($p, $t, (New-Object System.Text.UTF8Encoding $true))`.
* Не использовать `&&` / `||`, тернарник и `??` — в 5.1 их нет. Вместо `head`/`tail` —
  `Get-Content -TotalCount` / `-Tail`.
* Кириллицу в коде не передавать через `-Command "..."` — двойные кавычки съедают `$_`
  и ломают вложенный код; скрипты запускать через `-File`.

## Как работать

* Для поиска по коду — **Grep одним вызовом**, не циклы в шелле: каждый вызов шелла дёргает
  подтверждение прав и это раздражает.
* Не проверять то, что и так почти наверняка верно (уникальность свежесгенерированного GUID и т. п.).
* Не выдавать догадку за факт там, где исходник недоступен (скомпилированные формы, поведение
  сторонних подсистем).
